# 插件中心使用指南

DeepSeek Harness Studio 的插件中心直接管理当前 Windows 用户的 DSH `web` profile：

```text
%USERPROFILE%\.dsh\profiles\web
```

插件、Skills 和模型本身是三类不同能力：插件为 Harness 增加运行时工具或界面，Skills 为模型提供可发现的任务说明，模型与 API 则在 Harness 或对应组件设置中配置。

## 已安装

“已安装”页会扫描 `package.json`、`node_modules` 和 DSH bundle 列表，而不是只显示依赖名称。状态含义如下：

| 状态 | 含义 | 建议操作 |
| --- | --- | --- |
| 已启用 | 插件文件、清单和 bundle patch 均存在，且已加入 web profile | 可直接使用 |
| 已停用 | 插件仍安装在本机，但没有加载到运行时 | 打开开关即可重新启用 |
| 文件缺失 | profile 声明了依赖，但 `node_modules` 中没有对应文件 | 点击“修复插件”或“修复插件环境” |
| 不兼容 | 安装的是普通 npm 依赖，没有声明 `dsh.bundle.patch` | 确认来源；不需要时卸载 |
| 清单错误 | 插件 `package.json` 或 bundle patch 缺失/损坏 | 修复或重新安装插件 |
| 孤立条目 | bundle 已启用，但 dependencies 中没有对应依赖 | 点击清理按钮移除孤立条目 |
| 启动失败 | bundle patch 引用了当前 profile 无法加载的模块 | 点击“启动诊断”安全隔离，再尝试更新插件 |
| 已隔离 | 插件文件仍保留，但因加载检查失败而未加入运行时 | 更新修复后重新检查；通过检查才能启用 |

每张插件卡片可以打开真实安装目录；社区插件还可启停、更新、修复或卸载。内置核心组件不能被卸载或停用。

“启动诊断”首先解析每个社区插件的 bundle patch，并从当前 `web` profile 和插件目录验证 loader 模块是否可加载。若清单检查全部通过但 Harness 仍打不开，Studio 会继续执行真实启动探测：先确认核心组件可启动，再分组定位初始化崩溃或组件冲突，并只隔离导致失败的组件。安装、更新、修复、应用启动和手动重启都会使用同一套保护。

隔离记录保存在：

```text
%USERPROFILE%\.dsh\profiles\web\.studio-quarantine.json
```

隔离只会把插件从 bundle 列表中移出，依赖、插件文件和独立配置均不会删除。即使后续 DSH 包管理器在安装其他组件时重写 bundle 列表，Studio 也会根据隔离记录再次阻止已知故障插件加载。更新或修复该插件后会清除旧记录并重新进行真实启动验证；只有启动成功才会保持启用。

“修复插件环境”会补齐核心 bundle 并执行 DSH profile 安装，以恢复缺失依赖。若 profile 的 `package.json` 已损坏，Studio 会停止自动修复并提示先备份和手工修正，不会覆盖原文件。

## 生态组件

“生态组件”提供经过整理的固定版本入口。卡片会显示当前实际安装版本和健康状态：

- 未安装：一键接入；
- 已停用：一键重新启用；
- 已安装：按入口中的固定版本重新安装或修复；
- 状态异常：给出修复接入入口。

精选入口便于发现和复现，不代表 DeepSeek 官方背书。组件可能访问网络、工作区、命令执行或屏幕内容，安装前仍需检查其仓库、许可证和权限。

## 自定义导入

支持三种来源：

```text
npm:     @scope/dsh-plugin 或 @scope/dsh-plugin@1.2.3
GitHub:  github:owner/repository 或 https://github.com/owner/repository
本地:    通过“选择”按钮选取插件目录
```

本地目录会在安装前完成结构验证，必须满足：

1. 根目录存在可解析的 `package.json`；
2. `name` 是有效 npm 包名；
3. `dsh.bundle.patch` 指向实际存在且可解析的 patch 文件；
4. patch 声明的 loader 模块可以从插件自身或当前 profile 解析。

npm 和 GitHub 来源无法在下载前读取清单，因此“验证来源”只检查输入格式；安装完成后会立即执行相同的 DSH bundle 健康检查。若下载到的是普通依赖，插件中心会标记为“不兼容”，不会提供启用开关。

插件安装不会使用开发机固定路径。Node、DSH CLI、pnpm shim 和 profile 都从当前安装目录与当前 Windows 用户目录动态解析；若应用移动或覆盖安装，pnpm shim 会自动重写。v1.07.5 起，npm 官方源出现连接重置、超时、DNS 或网络不可达错误时，会自动切换 `https://registry.npmmirror.com` 重试；v1.07.6 起，即使 DSH 只返回 `pnpm failed in profile directory` 而没有保留底层网络代码，也会执行同一回退；v1.07.7 起，Windows 子进程使用唯一规范的 `Path` 键确保内置 pnpm 可见，并在两次 DSH 转发均失败后直接调用内置 pnpm。活动日志会显示本次操作实际使用的 Node 和 profile 路径。

## 活动与故障恢复

“活动”页显示当前操作、目标和 DSH/pnpm 输出。插件安装、更新、修复、卸载和启停期间，Studio 会暂时停止 Harness，操作结束后自动启动并验证其实际进入运行状态。若启动失败，界面会显示运行时诊断而不是误报操作成功。错误日志会保留在本次应用会话中，便于定位网络、版本、构建脚本或依赖问题。

常见处理顺序：

1. 点击“刷新列表”，确认是已停用还是异常；
2. 已停用时直接重新启用；
3. 出现“启动失败”时运行“启动诊断”，先隔离阻断项；
4. 文件缺失时先修复单个插件；
5. 多个依赖同时缺失时运行“修复插件环境”；
6. 查看“活动”日志；仍失败时打开 profile 和插件目录检查清单。

插件独立创建的 API Key、缓存和配置通常位于其自己的用户目录。卸载插件不会主动删除这些外部数据。
